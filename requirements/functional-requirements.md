# Functional Requirements
- Deploy this app to directory.pauldev.io
- Use design themes that are consistent with https://allsaintsorthodox.org/
- This is a church directory app where users can manage their own directory data, and they can also see the directory data of other users
- This is a multi-tenant app; in other words, it can support multiple organizations/churches
- There should be 3 types of users: Super Admin, Admin, and User
    - Super Admins: can create other Super Admins, Admins, Users, and organizations (and can assign admin users to an organization; each admin must be assigned to an organization); can also do everything that Admins and Users can do
    - Admins: can create users in their organization (both Admin and User user types); can edit information for other Users or Persons; can also do everything that Users can do
    - Users: can manage their own directory data and see the directory data of other users
- An individual user can be a part of a family; any user can create a family, and other users can associate themselves with any family
- A family can have people associated with it that aren't explicit users within the app (for example, a family might have children that don't have an account in the app); anyone in the family with a user account can manage the information for these non-user family members
- A Person (defined as either a user or a non-user family member) can have the following attributes: email, phone number, alternate phone number, first name, last name, address, patron saint, special dates
    - A Person that is a member of a family can choose to inherit the following attributes from another family member: email, phone number, alternate phone number, last name, address
- Special dates can be as follows:
    - Birthday (can optionally select month and day only or full month/day/year; checkbox should allow the person to opt-in to showing age to others; if opting-in to showing age, must select full month/day/year)
    - Wedding Anniversary (must select month/day/year)
        - When someone creates a wedding anniversary, that special date must link two Persons
    - Feast Day (month and day only)
- The app should have the following pages:
    - Directory: scrollable view of the entire directory, sorted by last name, with a search bar that matches anything in any data field
        - A checkbox narrows both the list and the search results to people who have an app account; unchecked by default, and kept in the page URL alongside the search so a filtered view can be shared, bookmarked and reloaded
    - Map view: a Google Maps view of where everyone lives
        - We will need to store lat/lon with addresses now (will need to use Google API for geocoding)
            - Google's terms only allow lat/lon to be cached for 30 days unless it is isolated to the one member who looked it up, which a shared parish map is not; place_id is separately exempt. So place_id is stored permanently and the coordinates are a cache refreshed daily. That daily job also geocodes any address that has never had coordinates -- a parish whose map was switched on later, or somebody who saved an address while Google was unreachable -- so nothing has to be triggered by hand.
        - Ideally need to have address completion at entry now to make sure addresses can be geocoded, but this is probably too expensive, so maybe fallback to attempting geocoding during save, and, if it fails, warn the user
        - The map view page is not a separate menu item; it's accessible from the directory page via tapping a map icon with "Map View" text
        - When the map view opens, it should be centered on the church and show approximately a 30 mile radius around the church
        - If no church address is saved, warn the admin and super admin that they need to save a church address; for map display when there is no church address, center on the centroid of all parishioners
        - This means we need to be able to associate an address for the church with each organization when it's created (or be able to edit an organization to add it)
        - If people share the exact same address AND are in the same family, show only the family name (and some kind of visual indicating that it's a family); If people share an address that aren't in the same family, you must show all of those people (could be a combination of multiple families, a family and an individual, etc.)
        - All identical addresses should share a pin, and when you tap on the pin, a popover opens beside it showing all family groups and/or individuals (as described above) that live there. A popover rather than a drawer or a side panel, on every size: those covered the map in order to describe a point on it, and on a phone a drawer took over half the screen to name one household. Being anchored to the marker also means the map pans itself if the popover would open off the edge.
            - An individual shows their photo, their name, and the address. A family shows the family name, a preview of the members who live there, and the address. The member preview reads "Anna, Maria, Nikolai +1" -- the same names-and-overflow the families list uses, in the same order the family page was dragged into, but with no count in front of it: a pin is an address, so a family with somebody living elsewhere would be described by a number that is true of the pin and false of the family. The family name links to the family, each individual's name to their record.
            - The address is stated once for the whole pin, since everybody there shares it, and is tappable in the same way an address is anywhere else in the app -- including asking which map app where both are plausible. It is Google's own formatting of the address rather than any one resident's typed version, because two people at one house can have typed it differently.
        - When close addresses are too close to distinguish on the map, show clusters (something like a circle with "5" indicating that there are 5 entities that live close); then, when you zoom in, they separate into distinct pins
        - The map fits the window it is in. It is measured rather than given a fraction of the viewport, because what sits above it varies: the header is 70px on a phone and up to 232px for a super admin, and an administrator may also be looking at a warning about the church address.
        - A full-screen button on the map, at every display size. Done in CSS rather than with the browser's Fullscreen API: iOS Safari will not take an element full screen, Google's own control hides itself below a size threshold, and the installed PWA has no browser chrome to leave -- so the native path fails on exactly the cases that want it most. Escape leaves, and the page underneath does not scroll while it is open.
        - This map view should be visually amazing and impressive
            - The base map is styled to the parish's own colours -- muted warm off-white, white roads, no business pins and no road shields -- so the pins are the most saturated thing on screen. A household is the liturgical red and somebody living alone is a lighter tint of it, so the two read as one set at two weights; gold is left for the church, which is then the only pin on the map that is not somebody's home. The church's pin has a popover too, giving the parish's name and its address as a link. That styling lives in the Google Cloud console against the Map ID, so it can be changed with no deploy; a copy of the JSON is committed at `docs/map-style.json` with the reasoning beside it.
    - Upcoming special dates
        - Shows list of upcoming dates within the next 7 days (today and the next 6 days); can optionally change the default range to whatever you want
        - Dates are grouped by date then special date type; if allowed, birthday and wedding anniversary date types show age and number of years respectively
        - Optionally a month-by-month calendar view as well that shows which dates have special dates in them, allows you to tap on a date, and it shows the special dates for that day under the calendar view
    - Prayer Requests
        - This is a page where members can create messages asking for others to pray for someone
        - A message should have a title, a message, and the ability to attach images
        - Once a prayer request has been submitted, it will need to be reviewed by a PRAYER_REQUEST_ADMIN (a new role; same privileges as MEMBER with the additional privilege of being able to approve prayer requests). Once the admin approves it, it should be shown on the prayer requests page to all members. Prayer requests should be ordered by "posted" time (i.e. the time that the approver approves the request). Store the submitted time in the database just in case we need it later.
        - When a new prayer request is posted, it should trigger a push notification to all members that have notifications enabled. The push notification should just say the number of new prayer requests, and, when you tap on the notification, it should open the installed PWA to the Prayer Requests page.
            - The notification's bold line reads "Prayer Requests" for a posted request and "Approval Needed" for one waiting on an approver; the message underneath is the count. The title must never be the app's own name: iOS composes that line as "{title} from {app name}" and cannot be told not to, so a title of "Parish Directory" rendered as "Parish Directory from Directory".
            - The author is notified too, when someone else approves their request -- being told your request is now up is the most useful notification the app sends. The only person not notified is whoever just posted it: the reviewer who approved it, or a reviewer posting their own request directly.
        - A PRAYER_REQUEST_ADMIN (and above) posts their own requests directly, with no separate approval step -- they are the person who would approve it, so routing it through review would only ask them to press a second button on their own words.
        - Create a notifications bell with a number badge in the top right nav of the app showing the number of notifications a user currently has. For prayer request notifications, for each prayer request notification, this should just show the title, and, when the notifications are viewed, the badge should go away (because the notifications have been read).
        - A PRAYER_REQUEST_ADMIN (and above) is also notified when a request is waiting for their approval -- bell and push, with its own notification tag so it does not displace a posted one. It clears itself the moment anyone decides the request, including another approver getting there first.
        - Approvers get their own switch for that, separate from the one for posted requests: "a request was posted for the parish" is news and "a request needs your approval" is a job, and somebody may reasonably want either without the other. The row is only shown to people who can approve; the copy says plainly that switching it off does not stop them approving, since the requests still appear on the page.
        - Nothing polls. The app updates three ways: a push notification, which the service worker forwards to any open tab; coming back to the app; and a refresh button (circular arrow) on the Prayer Requests page, which also says how old the list is. Polling was costed and dropped -- it scales with concurrent tabs rather than with events, and would have been the largest line item on the bill at ten thousand members to catch something that happens a few times a week.
            - Every relative timestamp is driven by a client-side clock that ticks while the tab is visible. Computed once at render they freeze, and a page left open ended up disagreeing with the bell about when the same request was posted, from identical data.
        - Only the last month of prayer requests should be shown. Keep them all in the database, but only show the last month in the app (based on posted date).
        - A reviewer can either post a request or decline it (optionally with a reason). The author sees their own requests until they are posted -- marked as waiting for review, or as declined with the reason -- and can withdraw any of them at any time. Nobody else sees a request until it is posted.
        - Each request is credited with its author's photo and name, both of which open that person's directory record. The photo is a rounded icon to the left of the whole card, the same shape the directory listing uses, so a name on a prayer request is a way into the directory rather than a dead end.
            - The photo links rather than enlarging: click-to-enlarge belongs on the person's own page, where a tap has nowhere else to go. It is also hidden from screen readers and skipped by the keyboard, since it leads exactly where the name beside it leads and a second link with the same name is one ambiguous target.
        - Notification settings live in the app, reached from a gear icon beside the notifications bell. One "Notifications" section holding two switches, in this order: what to be told about ("Prayer requests", which governs the bell and anything sent to a device), and where ("Push notifications" on this device). They compose, so the page says so rather than leaving somebody with push switched on and nothing selected to send.
            - Both have to be in the app rather than in iOS/Android settings. Permission can only be requested from a tap inside the app; the server has to be handed a push subscription, which the OS cannot give it; and "prayer requests specifically" has no OS equivalent. The system notification settings remain the global mute -- they can silence the installed app entirely, and the app cannot ask again once permission has been refused, so the settings page points at them when that happens.
            - On iOS, Web Push is only delivered to a PWA added to the home screen. In a Safari tab the settings page explains that instead of showing a switch that would do nothing.
            - Wherever push cannot be used -- not installed, permission refused, no keypair on the deployment, an incapable browser -- the page says *push* specifically and says the bell still works. Wording that reads as "notifications do not exist here" is wrong: they do, and the bell is unaffected in every one of those cases.
- Phone numbers should allow mobile users to tap to call that number
- A person's address should be tappable too, and open that address in a map.
    - Which map is asked rather than guessed. On an iPhone or iPad both Apple Maps and Google Maps are plausible and a web page cannot find out which of them is installed -- there is no API for it, and firing a custom scheme to see what happens cannot tell "not installed" from "slow to switch" -- so a tap offers the choice in a sheet, with a box to stop being asked. Everywhere else there is one sensible answer and the address is an ordinary link straight to it: a sheet offering a single option is a wasted tap.
    - A remembered choice is invisible once it stops asking, so Settings grows a row that names the map and takes the choice back. The row only exists for somebody who made one; a row saying there is nothing to reset is a row nobody needs. A choice that is no longer on offer -- Apple Maps, remembered on a phone, opened later on an Android tablet -- is ignored rather than followed to a web page nobody asked for.
    - A Mac is treated as a desk rather than as an Apple device, even though it ships Maps.app: the address opens in a tab, and a sheet is a question nobody standing in a parking lot would have been asked. Telling a Mac from an iPad needs the touch count, because since iPadOS 13 an iPad sends a Mac's user agent down to the WebKit build.
    - Every destination is an `https://` link rather than a `maps://` or `comgooglemaps://` one, so a tap that finds no app installed still lands on a web map instead of doing nothing at all. Android's own `geo:` chooser was considered and dropped for the same reason: when nothing claims the scheme the tap is a silent no-op, and the page cannot tell.
    - The Google Maps link opens in place on an iPhone or iPad, and only there. Every other link opens in a new tab so that a member who lands on a web map still has the directory behind it, but an installed copy of this app runs standalone, where a new tab is really an in-app web view -- and an in-app web view loads a universal link itself instead of handing it to the app that claims it. That is how choosing Google Maps came to open a web map that then bounced into the app. Apple Maps keeps its tab and was never affected: `maps.apple.com` is claimed by Maps.app below universal-link handling, from inside a web view or not. Nothing is lost on the one platform that changes, because iOS shows an off-scope navigation from a standalone app in an overlay that returns to the directory when it is dismissed.
    - An address with no street line is not linked. A city and state on their own resolve to the middle of the city, and a link that drops somebody four miles from the house is worse than plain text, because it looks like it knew.
    - Opening a map hands a member's home address to whoever they picked. That is the point of the feature, but it is worth saying out loud: Apple Maps is offered first where it exists, being the one certainly installed, and the link withholds the referrer so this page's own URL -- and the person's id in it -- does not travel along with the address.
