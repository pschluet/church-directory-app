# Functional Requirements
- Deploy this app to directory.pauldev.io
- Use design themes that are consistent with https://allsaintsorthodox.org/
- This is a church directory app where users can manage their own directory data, and they can also see the directory data of other users
- This is a multi-tenant app; in other words, it can support multiple organizations/churches
- There should be 3 types of users: Super Admin, Admin, and User
    - Super Admins: can create other Super Admins, Admins, Users, and organizations (and can assign admin users to an organization; each admin must be assigned to an organization); can also do everything that Admins and Users can do
    - Admins: can create users in their organization (both Admin and User user types); can edit information for other Users or Persons; can also do everything that Users can do
    - Users: can manage their own directory data and see the directory data of other users
- An individual user can be a part of a family; any user can create a family, and other users can associate themselves with any family
- A family can have people associated with it that aren't explicit users within the app (for example, a family might have children that don't have an account in the app); anyone in the family with a user account can manage the information for these non-user family members
- A Person (defined as either a user or a non-user family member) can have the following attributes: email, phone number, alternate phone number, first name, last name, address, patron saint, special dates
    - A Person that is a member of a family can choose to inherit the following attributes from another family member: email, phone number, alternate phone number, last name, address
- Special dates can be as follows:
    - Birthday (can optionally select month and day only or full month/day/year; checkbox should allow the person to opt-in to showing age to others; if opting-in to showing age, must select full month/day/year)
    - Wedding Anniversary (must select month/day/year)
        - When someone creates a wedding anniversary, that special date must link two Persons
    - Feast Day (month and day only)
- The app should have the following pages:
    - Directory: scrollable view of the entire directory, sorted by last name, with a search bar that matches anything in any data field
        - A checkbox narrows both the list and the search results to people who have an app account; unchecked by default, and kept in the page URL alongside the search so a filtered view can be shared, bookmarked and reloaded
    - Upcoming special dates
        - Shows list of upcoming dates within the next 7 days (today and the next 6 days); can optionally change the default range to whatever you want
        - Dates are grouped by date then special date type; if allowed, birthday and wedding anniversary date types show age and number of years respectively
        - Optionally a month-by-month calendar view as well that shows which dates have special dates in them, allows you to tap on a date, and it shows the special dates for that day under the calendar view
    - Prayer Requests
        - This is a page where members can create messages asking for others to pray for someone
        - A message should have a title, a message, and the ability to attach images
        - Once a prayer request has been submitted, it will need to be reviewed by a PRAYER_REQUEST_ADMIN (a new role; same privileges as MEMBER with the additional privilege of being able to approve prayer requests). Once the admin approves it, it should be shown on the prayer requests page to all members. Prayer requests should be ordered by "posted" time (i.e. the time that the approver approves the request). Store the submitted time in the database just in case we need it later.
        - When a new prayer request is posted, it should trigger a push notification to all members that have notifications enabled. The push notification should just say the number of new prayer requests, and, when you tap on the notification, it should open the installed PWA to the Prayer Requests page.
            - The author is notified too, when someone else approves their request -- being told your request is now up is the most useful notification the app sends. The only person not notified is whoever just posted it: the reviewer who approved it, or a reviewer posting their own request directly.
        - A PRAYER_REQUEST_ADMIN (and above) posts their own requests directly, with no separate approval step -- they are the person who would approve it, so routing it through review would only ask them to press a second button on their own words.
        - Create a notifications bell with a number badge in the top right nav of the app showing the number of notifications a user currently has. For prayer request notifications, for each prayer request notification, this should just show the title, and, when the notifications are viewed, the badge should go away (because the notifications have been read).
        - A PRAYER_REQUEST_ADMIN (and above) is also notified when a request is waiting for their review -- bell and push, on the same "Prayer requests" switch, with its own notification tag so it does not displace a posted one. It clears itself the moment anyone decides the request, including another reviewer getting there first.
        - Nothing polls. The app updates three ways: a push notification, which the service worker forwards to any open tab; coming back to the app; and a refresh button (circular arrow) on the Prayer Requests page, which also says how old the list is. Polling was costed and dropped -- it scales with concurrent tabs rather than with events, and would have been the largest line item on the bill at ten thousand members to catch something that happens a few times a week.
            - Every relative timestamp is driven by a client-side clock that ticks while the tab is visible. Computed once at render they freeze, and a page left open ended up disagreeing with the bell about when the same request was posted, from identical data.
        - Only the last month of prayer requests should be shown. Keep them all in the database, but only show the last month in the app (based on posted date).
        - A reviewer can either post a request or decline it (optionally with a reason). The author sees their own requests until they are posted -- marked as waiting for review, or as declined with the reason -- and can withdraw any of them at any time. Nobody else sees a request until it is posted.
        - Notification settings live in the app, reached from a gear icon beside the notifications bell. One "Notifications" section holding two switches, in this order: what to be told about ("Prayer requests", which governs the bell and anything sent to a device), and where ("Push notifications" on this device). They compose, so the page says so rather than leaving somebody with push switched on and nothing selected to send.
            - Both have to be in the app rather than in iOS/Android settings. Permission can only be requested from a tap inside the app; the server has to be handed a push subscription, which the OS cannot give it; and "prayer requests specifically" has no OS equivalent. The system notification settings remain the global mute -- they can silence the installed app entirely, and the app cannot ask again once permission has been refused, so the settings page points at them when that happens.
            - On iOS, Web Push is only delivered to a PWA added to the home screen. In a Safari tab the settings page explains that instead of showing a switch that would do nothing.
            - Wherever push cannot be used -- not installed, permission refused, no keypair on the deployment, an incapable browser -- the page says *push* specifically and says the bell still works. Wording that reads as "notifications do not exist here" is wrong: they do, and the bell is unaffected in every one of those cases.
- Phone numbers should allow mobile users to tap to call that number
